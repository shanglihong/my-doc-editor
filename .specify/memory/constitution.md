# My Docs 项目宪章

## Core Principles

### 原则一：代码质量至上 (Code Quality Excellence)
恪守 KISS（Keep It Simple, Stupid）原则与 DRY（Don't Repeat Yourself）原则，崇尚代码简洁性与高可维护性。严禁过度工程化与不必要的防御性设计。所有代码必须具备高可读性、高内聚与低耦合，模块边界清晰。任何技术抽象与重构必须基于真实的业务场景与可复用需求，而非预测未来不确定性。

### 原则二：严格测试标准 (Rigorous Testing Standards)
坚持质量左移与测试驱动理念。核心业务逻辑、公共库及关键交互组件必须具备完整的自动化单元测试与集成测试覆盖。测试用例必须具备确定性、独立性与可重复执行性。严禁为了通过构建而删除失败测试、掩盖异常或使用无效断言，代码变更必须经过测试验证后方可提交。

### 原则三：用户体验一致性 (UX Consistency & Modern Design)
致力于提供视觉出众、交互流畅、体验一致的高品质用户界面。统一遵循项目设计规范与视觉语言（统一排版、色彩体系与组件库），确保跨页面与设备的响应式表现。交互流程须保持直观与可预测，重视微交互与细节反馈，边界异常须提供清晰且有建设性的用户提示。

### 原则四：高性能与高响应性 (Performance & Responsiveness)
性能是产品的核心体验。前端应用需严格控制资源体积，优化首屏加载性能与渲染帧率；后端与服务接口需控制计算复杂度与网络开销。严禁在主界面或主线程中执行阻塞性同步操作。关键路径性能指标必须有明确标准，性能退化视为阻断性问题。

### 原则五：架构简洁性与演进 (Architectural Simplicity)
立足第一性原理剖析技术方案，优先采用简单、成熟且经过验证的技术栈与架构模式。新增第三方依赖或引入复杂架构构件前，必须评估其维护成本与必要性。保持架构的演进能力，以最小可扩展设计满足当前业务诉求。

### 原则六：规范与文档中文表达 (Specification & Language Standards)
项目中后续所有的需求规范（Spec）、实施计划（Plan）、任务分解（Tasks）、架构设计及技术文档，均必须统一使用中文进行编写、评审与维护，以确保团队沟通高效精准、语义消除歧义并保持一致上下文。

## 质量门禁与技术决策框架

技术决策与实施方案的选择必须以本宪章原则为指导依据：
1. **方案评估矩阵**：所有重大设计方案（Plan）必须明确评估对代码质量、测试覆盖、UX一致性及性能指标的影响。
2. **决策优先级**：当技术方案存在冲突时，优先级排序为：用户体验与可靠性 > 代码质量与可维护性 > 开发速度。
3. **破坏性变更特批**：任何违背或削弱既有宪章原则的技术方案，必须提出书面理由与替代方案对比，经团队评审特批后方可实施。

## 开发工作流与实施规范

1. **结构化开发流程**：严格遵循“构思方案 → 提请审核 → 分解任务 → 编码实现 → 自动化验证”的顺序作业。
2. **中文文档贯穿全流程**：需求分析（specify）、方案设计（plan）及任务拆解（tasks）阶段的产出物均须全中文撰写。
3. **代码审查标准**：代码审查（Code Review）必须依据本宪章的质量与测试原则，对代码规范、覆盖率、潜在性能瓶颈进行全面检查。
4. **持续集成验证**：合并至主干前，必须通过自动化测试、静态代码分析以及构建校验。

## Governance

1. **最高效力**：本宪章高于项目中的任何日常开发习惯或临时口头约定。项目中所有的 Spec 规范、实施计划（Plan）及任务分解（Tasks）均须遵循本宪章。
2. **修订机制**：宪章的修订需提出明确的修订草案，说明修订原因与影响范围。版本变更遵循语义化版本规范：
   - MAJOR：重大原则变更或删减，涉及不兼容的治理规则调整。
   - MINOR：新增原则、补充重要的实施要求或框架扩展。
   - PATCH：文字精炼、格式修正或非实质性的内容澄清。
3. **合规审查**：在日常开发与需求实施过程中，项目成员与 AI 代理均须定期对照本宪章检查代码与架构合规性，确保 Spec 及其衍生文档符合中文规范要求。
